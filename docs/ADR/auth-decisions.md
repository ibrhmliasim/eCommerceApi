## AUTH — Architectural Decision Records

### AUTH-0: Выбор SPA Cookie-based (Stateful) авторизации через Laravel Sanctum

**Status:** Accepted

**Контекст:**
При проектировании авторизации для decoupled-архитектуры (Фронтенд на Next.js и Бэкенд на Laravel API) на продакшене (VPS) используется топология единого базового домена с поддоменами:

- Frontend: `yourshop.com` (или локальный `yourshop.test:3000`)
- Backend API: `api.yourshop.com` (или локальный `api.yourshop.test:8000`)

Нам необходимо было выбрать между Stateless-авторизацией (Personal Access Tokens / Bearer JWT в заголовках) и Stateful-авторизацией (сессионные куки через Laravel Sanctum).

**Выбрали:**
Стратегический выбор сделан в пользу **SPA Cookie-based Auth (Stateful)** с использованием стандартного сессионного гарда Laravel (`Auth::guard('web')`) и мидлваря `EnsureFrontendRequestsAreStateful`.

**Почему (Архитектурные преимущества):**

1. **Железобетонная безопасность (Защита от XSS):** При использовании токенов фронтенд вынужден хранить их в `localStorage` или `sessionStorage`. В случае успешной XSS-атаки (внедрение вредоносного JS-скрипта через стороннюю библиотеку) токен пользователя будет мгновенно украден.
   Куки с флагами `HttpOnly` и `Secure` физически **недоступны для чтения из JavaScript**. Даже если на фронтенде произойдет XSS-уязвимость, злоумышленник не сможет угнать сессию пользователя.
2. **Автоматический Cross-Domain шеринг:** Так как Next.js и Laravel делят один базовый домен, кука сессии выставляется на уровне `.yourshop.com` (с точкой в начале). Браузер пользователя нативно и автоматически прикрепляет эту куку к каждому API-запросу от Next.js к бэкенду. Нам не нужно писать кастомный JS-код для менеджмента и обновления токенов.
3. **Framework-Native встроенная защита от CSRF:**
   Sanctum из коробки принуждает фронтенд делать предварительный запрос к эндпоинту `/sanctum/csrf-cookie`. Это создаёт криптографический `XSRF-TOKEN`, защищая e-commerce API от межсайтовой подделки запросов (когда пользователя завлекают на фишинговый сайт, пытающийся незаметно отправить запрос на покупку/смену пароля в твоем магазине).
4. **Снижение I/O нагрузки на БД (Связка с Redis):**
   В отличие от Personal Access Tokens, которые при каждом запросе дергают базу данных SQL для сверки токена, сессии Sanctum хранятся в Redis (оперативной памяти). Это обеспечивает мгновенный ответ API на высоконагруженных e-commerce эндпоинтах.

**Компромиссы / Отказ от альтернатив (Trade-offs):**

- **Отказ от токенов (Bearer Tokens):** Мы осознанно отказались от генерации `$user->createToken()`, так как проект не является публичным API для сторонних интеграторов и на текущем этапе не имеет мобильного приложения. В случае появления мобильного клиента (iOS/Android), Sanctum позволит бесшовно обрабатывать Bearer-токены на тех же роутах, не ломая текущую Cookie-логику для Next.js.
- **Сложность локальной разработки:** Требует настройки локальных доменов через файл `hosts` (`yourshop.test`) вместо дефолтного `localhost`, чтобы браузер корректно обрабатывал междоменные куки.

**Конфигурационный контракт (Критические настройки):**

- `config/cors.php`: `supports_credentials => true` (разрешает браузеру передавать куки в CORS-запросах).
- `config/cors.php`: `allowed_origins => [env('FRONTEND_URL')]` (строгое ограничение доверенного домена Next.js).
- `.env`: `SANCTUM_STATEFUL_DOMAINS=yourshop.com,api.yourshop.com` (список доменов, для которых Sanctum активирует сессионную проверку).

### AUTH-1: Использование Signed URL с TrustProxies конфигурацией (email verification и password reset) — v1

**Status:** Superseded by AUTH-13

**Выбрали:** Стандартный `URL::temporarySignedRoute` + доверие прокси (`$middleware->trustProxies(at: '*')`).

**Почему (Архитектурные преимущества):**

- **Просто и нативно:** Используем встроенный механизм Laravel (подпись через HMAC-SHA256 + middleware `signed`). Ничего не изобретаем — всё работает "из коробки".
- **Без БД (stateless):** Не храним токены/коды. Laravel проверяет ссылку по подписи и `APP_KEY` → нет таблиц, cron и лишних запросов.
- **Безопаснее, чем OTP:** Нельзя перебрать как 6-значный код. Любое изменение URL ломает подпись → доступ запрещён.
- **Корректная работа за прокси:** `trustProxies` решает проблему `http/https` и домена (через `X-Forwarded-*`), убирая ошибки `403 Invalid Signature`.

**Trade-off (Компромиссы):**

- В письме отправляется полный URL с подписью (`?signature=...`). Это чувствительные данные, которые могут остаться в истории браузера.

**Смягчение рисков (Mitigation):**

- **Frontend как прокси:** Next.js принимает ссылку, отправляет данные на backend и не раскрывает прямой API flow.
- **Очистка URL:** После верификации выполняем `router.replace('/auth/verify-email?status=success')`, убирая подпись из истории браузера.

### AUTH-2: POST-only endpoint для верификации email

**Status:** Accepted

**Выбрали:** Использование метода `POST /api/v1/auth/email/verify` вместо классического `GET`.

**Почему (Защита от почтовых роботов-сканеров):**

- **Проблема GET-метода:** Современные корпоративные почтовые клиенты и антивирусы (Outlook Safe Links, Gmail Scanner, Slack unfurl) автоматически «кликают» по всем ссылкам в логах и входящих письмах, чтобы проверить их на фишинг. Если верификация работает через `GET`, робот сам подтвердит почту за пользователя еще до того, как тот откроет письмо.
- **Решение через POST:** Роботы-сканеры выполняют исключительно `GET`-запросы для парсинга страниц. Они физически не умеют и не станут отправлять `POST`-запросы с изменением состояния. Это гарантирует, что email будет верифицирован только тогда, когда реальный пользователь зайдет на страницу фронтенда.

**Trade-off (Компромиссы):**

- Изменение стандартного поведения Laravel «из коробки» (так как фреймворк по умолчанию генерирует GET-ссылки для верификации). Требуется кастомизация роутинга и явное разделение UI-слоя и API-слоя.

**Контракт и обязательства фронтенда (Mitigation):**

- Страница Next.js (`/auth/verify-email`) служит исключительно как UI-оболочка.
- При маунте (загрузке) страницы или по клику на кнопку фронтенд обязан перехватить query-параметры и триггернуть именно `POST`-запрос на API бэкенда. Автоматический POST при маунте разрешен, так как роботы-сканеры не исполняют сложный JS-код фронтенда для отправки API-запросов.

### AUTH-3: Установление времени жизни (TTL) верификационной ссылки в 60 минут — v1

**Status:** Superseded by AUTH-14

**Выбрали:** `now()->addMinutes(60)`

**Почему (Баланс безопасности и бизнес-конверсии):**

- **UX и Конверсия:** Лимиты в 10–15 минут (стандартные для сброса пароля) создают высокий процент ложных ошибок "Link Expired" в e-commerce. Письма от почтовых серверов (особенно в пиковые распродажи) могут идти до клиента 5–7 минут. Пользователь также может отвлечься. Часовой лимит минимизирует барьеры для легитимных покупателей.
- **Индустриальный стандарт:** Для сценария первичной верификации аккаунта (регистрации) 60 минут является общепринятым стандартом среди крупных платформ, так как это действие не открывает мгновенный доступ к смене критических данных (паролей, платежных карт).

**Trade-off (Компромиссы):**

- Увеличивается временное «окно атаки». Если подпись (`signature`) утечет в логи или историю, у злоумышленника есть целый час, чтобы попытаться отправить запрос вместо пользователя.

**Почему риск приемлем (Защита на уровне бизнес-логики):**

- **Идемпотентность бэкенда:** Метод `markEmailAsVerified()` в Laravel работает как чистая функция изменения состояния. Если реальный пользователь уже подтвердил почту (что занимает у него обычно 1–2 минуты), повторный запрос по этой же ссылке от злоумышленника вернет ошибку `409 Conflict` (`email_already_verified`).
- Таким образом, «окно атаки» в 60 минут схлопывается до **0 минут** в ту же секунду, когда легитимный пользователь успешно завершил флоу верификации. Ссылка моментально становится бесполезной для повторного использования.

### AUTH-4: Архитектурный контракт MustVerifyEmail и ручной диспатч события Registered — v1

**Status:** Superseded by AUTH-15

**Выбрали:**
Реализация стандартного интерфейса `Illuminate\Contracts\Auth\MustVerifyEmail` на модели `User` в сочетании с явным ручным вызовом `event(new Registered($user))` внутри сервисного слоя (`AuthService`).

**Почему (Контроль транзакций и предсказуемость флоу):**

- **Изоляция по принципу ACID:**
  В отличие от автоматических триггеров моделей (Eloquent Observers), ручной диспатч события в `AuthService` гарантирует, что уведомление о верификации будет отправлено строго после того, как процесс регистрации пользователя полностью завершён и все сопутствующие транзакции успешно закоммичены в БД.
- **Защита от Race Conditions:**
  Это исключает критический баг, когда системный листенер перехватывает событие и пытается отправить письмо, пока транзакция создания пользователя ещё не закрыта. В этот момент фоновый воркер может не найти пользователя в базе данных и упасть с ошибкой `ModelNotFoundException`.

**Чистый контракт модели:**
Метод `sendEmailVerificationNotification()` переопределён внутри класса `User` только для подмены дефолтного класса нотификации на кастомный `VerifyEmailNotification`, адаптированный под относительные ссылки Next.js (см. AUTH-1).

**Trade-off (Компромиссы):**
Повышается человеческий фактор при расширении API. Если в будущем будет добавлен альтернативный способ регистрации (например, через Socialite / OAuth / Google Sign-In), разработчик обязан не забыть вручную вызвать `event(new Registered($user))` в новом методе — иначе письмо верификации не отправится.

**Урок конфигурации — Инфраструктура:**
В Laravel 11/12+ старый `EventServiceProvider` упразднён. Для того чтобы ручной диспатч системного события `Registered` корректно связался со встроенным листенером фреймворка (`SendEmailVerificationNotification`), в `bootstrap/app.php` зафиксировано автоматическое обнаружение:

```php
->withEvents(discover: [
    __DIR__.'/../app/Listeners',
])
```

**Это гарантирует корректное кэширование связей событий командой `php artisan event:cache` на продакшене.**

### AUTH-5: Синхронная отправка email-уведомлений на этапе MVP / Разработки

**Status:** Accepted

**Выбрали:** Не использовать `ShouldQueue` в кастомных уведомлениях и выполнять отправку email синхронно (в рамках HTTP-запроса).

**Почему (Прагматизм разработки и барьеры отладки):**

- **Queue требует worker:** Интерфейс `ShouldQueue` не выполняет задачу сам — он лишь помещает её в очередь. Без запущенного процесса (`php artisan queue:work` или `queue:listen`) задачи не обрабатываются и письма не отправляются.
- **Проблема драйвера `database`:** При использовании `database` driver задачи накапливаются в таблице `jobs`, создавая ложное ощущение, что система работает, хотя фактической отправки не происходит.
- **Operational Complexity (Операционная сложность):** Поддержка очередей в dev/CI требует запуска и мониторинга воркеров (часто внутри Docker), что усложняет среду и отвлекает от разработки бизнес-логики.
- **Прозрачность отладки:** В синхронном режиме ошибки SMTP (неверные ключи, таймауты, сетевые проблемы) сразу проявляются в HTTP-ответе или логах, обеспечивая быстрый feedback.

**Trade-off (Компромиссы):**

- **Блокировка потока (Latency):** Отправка email увеличивает время ответа на регистрацию (~200–500ms), так как выполняется в рамках запроса. Для MVP и тестовой среды это допустимо.

**Условия возврата очередей (Trigger для рефакторинга):**
Архитектурное решение будет пересмотрено при переходе проекта в стадию **Production/Staging** при выполнении следующих условий:

1. Использование **Redis** в качестве брокера очередей (`QUEUE_CONNECTION=redis`).
2. Наличие стабильного worker-процесса (через **Supervisor** или **Laravel Horizon**).
3. Рост нагрузки, при котором синхронная отправка начинает негативно влиять на время ответа и UX.

**Примечание (2026-07-31):** `ShouldQueue` уже реализован на `VerifyEmailNotification`/`WelcomeNotification` с самого начала — при `QUEUE_CONNECTION=sync` интерфейс присутствует архитектурно, но неактивен (job исполняется немедленно в том же процессе). Это не выбор "sync вместо async", а "async путь предусмотрен, но отложенно активируется" — см. `architecture-learnings.md`.

### AUTH-6: Бизнес-логика verify/resend в контроллере

**Status:** Accepted

**Выбрали:** Не выносить в `AuthService`

**Почему:** Email verification — отдельный домен. Смешивать с `AuthService` нарушает SRP

**Trade-off:** Небольшое отклонение от правила "тонкий контроллер"

**Граница:** `AuthService` отвечает за register/login/logout. Верификация — отдельная ответственность

**Когда пересматривать (Триггер для рефакторинга):**
Если логика верификации начнет обрастать сложными бизнес-требованиями. Например: начисление бонусных баллов за подтверждение почты, автоматическое создание профиля покупателя в CRM-системе (Bitrix/Amo) через API-запрос, или отправка цепочки маркетинговых писем. При возникновении этих условий логика будет вынесена из контроллера в отдельный специализированный `EmailVerificationService` (но НЕ в `AuthService`).

### AUTH-7: Одновременная отправка Welcome-письма и ссылки верификации при регистрации — v1

**Status:** Superseded by AUTH-16

**Выбрали:** Отправка двух независимых уведомлений (`VerifyEmailNotification` и `WelcomeNotification`) сразу в момент наступления события `Registered`.

**Почему (UX-приоритет быстрого вовлечения):**

- **Мгновенный онбординг:** Пользователь сразу получает подтверждение, что его личный кабинет создан (Welcome), и параллельно получает техническую ссылку для активации аккаунта. Это создает ощущение отзывчивого и быстрого интерфейса.
- **Маркетинговый контекст:** В e-commerce важно зафиксировать интерес покупателя в «горячей» фазе. Welcome-письмо может сразу содержать первый приветственный купон на скидку, стимулируя пользователя быстрее пройти верификацию и вернуться на сайт для покупки.

**Trade-off (Риски и компромиссы):**

- **Склеивание писем (Email Threading):** Почтовые клиенты (Gmail, Outlook) из-за одинакового отправителя и минимального временного зазора могут объединить оба письма в одну цепочку. Из-за этого пользователь может физически не заметить техническую ссылку верификации, скрытую под Welcome-шаблоном.
- **Нагрузка на репутацию SMTP-домена:** Отправка писем еще не верифицированным (потенциально фейковым или «битым») пользователям создает лишний трафик на SMTP-шлюз и может незначительно снижать спам-рейтинг домена бэкенда.

**Смягчение рисков (Mitigation):**

- **Разделение тем (Subject Lines):** Мы используем кардинально разные темы писем (например, _"Успешная регистрация в YourShop!"_ и _"Подтвердите ваш email для активации аккаунта"_), чтобы минимизировать шанс склеивания цепочки почтовыми роботами.
- **Визуальный акцент на фронтенде:** Экран Next.js после успешной регистрации жестко фокусирует внимание пользователя: _"Мы отправили вам письмо для подтверждения. Пожалуйста, проверьте почту перед тем, как воспользоваться приветственными бонусами"_.

**Когда пересматривать (Триггеры для рефакторинга):**

1. Если продуктовая аналитика (Product Analytics) покажет низкий процент завершения верификации (Verification Rate < 70-80%) из-за того, что пользователи «теряются» в двух письмах.
2. Переход на **Флоу последовательной отправки (Sequential Flow)**: Welcome-письмо с бонусами отправляется строго _после_ того, как сработает событие `Illuminate\Auth\Events\Verified` (почта успешно подтверждена). Это считается более чистой практикой с точки зрения гигиены базы подписчиков.

### AUTH-8: Гранулярное применение middleware 'verified' (Изоляция критических бизнес-процессов) — v1

**Status:** Superseded by AUTH-17

**Выбрали:** Точечное (гранулярное) назначение middleware `verified` исключительно на эндпоинты оформления и оплаты заказов, вместо глобальной блокировки сессии пользователя.

**Почему (Приоритет UX-свободы и бизнес-конверсии):**

- **Предотвращение «Тупика авторизации» (Dead End UX):** Если заблокировать базовые роуты (`/me`, `/logout`), пользователь, совершивший ошибку в email при регистрации, не сможет выйти из аккаунта или изменить данные. Система должна сохранять доступ к профилю и механизму завершения сессии в любом состоянии аккаунта.
- **Снижение барьеров для корзины (Soft Onboarding):** В e-commerce критически важно дать пользователю возможность свободно собирать корзину, просматривать каталог и изучать личный кабинет без жестких технических ограничений. Наполнение корзины — это намерение совершить покупку, и его нельзя прерывать требованием верификации.
- **Четкая граница ответственности:** Верификация почты защищает бизнес от фейковых заказов, спама в платежные шлюзы и мошенничества (Fraud Prevention). Поэтому защита включается строго на этапе перехода к транзакциям (Checkout / Payments).

**Контракт доступа к API-маршрутам:**

| Группа API маршрутов      | Эндпоинты                                   | Требуется `auth:sanctum` | Требуется `verified` | Обоснование                                                                             |
| :------------------------ | :------------------------------------------ | :----------------------: | :------------------: | :-------------------------------------------------------------------------------------- |
| **Public Catalog**        | `GET /products`, `/categories`              |            ❌            |          ❌          | Доступно для гостей и поисковых роботов SEO.                                            |
| **Auth & Verification**   | `/login`, `/register`, `/verify`, `/resend` |            ❌            |          ❌          | Базовые механизмы управления доступом.                                                  |
| **Session & Profile**     | `GET /me`, `POST /logout`, `/profile/edit`  |            ✅            |          ❌          | Разрешено менять данные профиля и выходить из системы.                                  |
| **Cart Operations**       | `GET/POST /cart`                            |            ✅            |          ❌          | Наполнение корзины не требует подтвержденного email.                                    |
| **Checkout & Financials** | `POST /checkout`, `/orders`, `/payments`    |            ✅            |          ✅          | **Критическая зона.** Проведение транзакций разрешено только верифицированным клиентам. |

**Trade-off (Компромиссы):**

- Неверифицированные пользователи могут генерировать «мусорные» записи в таблице корзин или адресов (если они сохраняются до чекаута). Нагрузка на базу данных контролируется фоновыми процессами очистки брошенных корзин.

**Когда добавлять и контролировать:**
Контракт вступает в силу немедленно. При создании контроллеров для оформления заказа (`OrderController`, `CheckoutController`) middleware `verified` (или кастомное API-расширение, возвращающее JSON 403 вместо редиректа) должно внедряться на уровне роутинга API.

### AUTH-9: Инвалидация сессий на всех устройствах при смене пароля

**Status:** Accepted

**Выбрали:** Прямое удаление записей через `DB::table('sessions')->where('user_id', $user->id)->delete()` при сбросе пароля или бане пользователя.

**Почему (Прагматизм для Database Driver):**

- **Мгновенный эффект:** Поскольку текущий стек использует драйвер `database` для сессий (в таблице `sessions` есть явное поле `user_id`), один SQL-запрос мгновенно уничтожает все активные токены/сессии пользователя на всех устройствах (десктоп, мобилка, планшет). При следующем запросе фронтенд Next.js получит валидный `401 Unauthorized`.
- **KISS (Keep It Simple, Stupid):** Это решение требует ровно одну строчку кода в сервисе/контроллере и не создает никакой дополнительной логической нагрузки на систему.

**Trade-off (Компромиссы):**

- **Блокировка при масштабировании:** При росте онлайна постоянные операции `DELETE` в реляционной таблице `sessions` могут вызывать блокировки строк (row locks) и нагружать диск (I/O).
- **Привязка к драйверу:** Этот код жестко завязан на структуру таблицы SQL и полностью перестанет работать, как только проект переключится на высокопроизводительный `SESSION_DRIVER=redis`.

**Как это будет пересматриваться (Production-ready Redis стратегия):**
При переходе на Redis мы **НЕ будем** вводить поле `session_version` в таблицу пользователей и писать кастомные middleware (так как это создаст лишний `SELECT` запрос в БД на каждый чих пользователя, убивая весь смысл кэширования).

Вместо этого будет реализован **Сессионный индекс (User-to-Session Mapping)** средствами Redis:

1. При авторизации хэш сессии пользователя автоматически добавляется в Set-структуру Redis с ключом `user:sessions:{user_id}`.
2. При смене пароля бэкенд за одну операцию $O(1)$ запрашивает этот Set, берет все хэши сессий конкретного юзера и делает для них `DEL`.
3. Это инвалидирует все устройства за микросекунды, вообще не трогая основную базу данных MySQL.

### AUTH-10: Унификация ответов (Unified Error Messages) на сбросе пароля и защита от атак по сторонним каналам

**Status:** Accepted

**Выбрали:** Возврат идентичных ответов `200 OK` с текстом `auth.reset_link_sent` для эндпоинта `password/forgot` при любых исходах работы внутреннего брокера Laravel (Успех, Несуществующий Email, Внутренний Throttle брокера).

**Почему (Защита от Side-Channel State Attacks):**

- Если возвращать статус `429` или менять текст ошибки при ответе брокера `Password::RESET_THROTTLED`, система выдаст факт существования аккаунта. Атакующий сможет определить валидность email по поведению внутреннего таймера токенов. Полная маскировка состояний брокера внутри контроллера гарантирует нулевую утечку данных (Zero-Knowledge).

**Смягчение рисков (Защита SMTP):**

- Для защиты сервера от лавинообразного спама эндпоинты `password/forgot` и `password/reset` защищены сетевым мидлварем `throttle:5,1`.
- Ограничение частоты работает строго на уровне входящего IP-адреса. Если один и тот же клиент совершает более 5 запросов в минуту, мидлварь жестко возвращает **`429 Too Many Requests`** независимо от передаваемых в теле запроса email-адресов. Это полностью изолирует сетевую защиту от бизнес-логики базы данных.

### AUTH-11: Допущение User Enumeration на этапе регистрации ради UX и поддержки Soft Deletes

**Status:** Accepted

**Выбрали:** Стандартная валидация уникальности email `Rule::unique('users', 'email')->whereNull('deleted_at')` с возвратом явной ошибки `422 Unprocessable Entity` (_"Этот email уже занят"_).

**Почему (Приоритет продуктового UX и гигиены данных):**

- **Продуктовый UX:** Попытка скрыть существование email при регистрации (например, возврат `200 OK` и отправка скрытого письма «Вы уже зарегистрированы») критически усложняет флоу для реального клиента. Пользователь должен мгновенно видеть ошибку ввода, чтобы переключиться на форму логина или исправить опечатку.
- **Бизнес-логика Soft Deletes:** Мы используем мягкое удаление пользователей. Если клиент удалил свой старый профиль (`deleted_at` не null), его email криптографически освобождается. Наличие скоупа `whereNull` гарантирует, что бывший клиент сможет зарегистрироваться заново с чистого листа, не создавая конфликтов в БД.

**Trade-off (Риски информационной безопасности):**

- Эндпоинт `POST /api/v1/auth/register` становится уязвимым к атакам перебора (User Enumeration). Злоумышленник может программно проверять списки email-адресов на предмет того, являются ли их владельцы клиентами нашего магазина.

**Смягчение рисков (Mitigation):**

- **Агрессивный Rate Limiting:** На эндпоинт регистрации накладывается жесткий лимит запросов через Redis — `throttle:10,1` (максимум 10 попыток в минуту на один IP-адрес / сессию). Это делает брутфорс масштабных баз данных экономически и технически неэффективным для атакующего.
- **Асимметричная защита доменов:** Уязвимость локализована исключительно на этапе регистрации. Эндпоинты сброса пароля (**AUTH-10**) при этом остаются полностью защищенными и возвращают универсальные generic-ответы.

**Примечание:** С переходом на zero-DB-write registration (AUTH-17) семантика этого риска сузилась — `422` на `/register` теперь означает существующего активного `User`, а не просто незавершённую регистрацию. Сам факт enumeration-уязвимости остаётся, mitigation не меняется.

### AUTH-12: Игнорирование тела ответа Login/Register — единственный источник правды через `/me` — v1

**Status:** Superseded by AUTH-18

**Контекст:**
`AuthController::login()` и `AuthController::register()` возвращают `UserResource` — тот же самый Resource, который отдаёт `AuthController::me()`. Технически фронтенд получает полные данные пользователя сразу в ответе на `/login` и `/register`, но намеренно их не использует: `sessionApi.login()` и `sessionApi.register()` типизированы как `Promise<void>`.

Вместо чтения тела ответа, `onSuccess` мутаций вызывает `queryClient.invalidateQueries()`, что триггерит отдельный `GET /me` — то есть бэк повторно собирает и отправляет тот же самый `UserResource` вторым запросом.

**Выбрали:**
Осознанное дублирование HTTP-запроса ради единственного источника правды (single source of truth) для данных пользователя — только через `useMeQuery`.

**Почему (Архитектурные преимущества):**

1. **Устойчивость к повторным визитам:** Если у пользователя уже есть активная Sanctum-сессия (кука жива), но он открывает сайт заново — `login`/`register` не вызываются вообще. Единственный способ узнать "кто я" — спросить бэк через `/me`. Если бы данные писались в кэш только из `login`/`register`, при повторном визите кэш остался бы пустым.
2. **Консистентность между вкладками:** TanStack Query cache не шарится между вкладками браузера. Вкладка, залогинившаяся через форму, не может "поделиться" данными юзера с уже открытой соседней вкладкой напрямую — обе полагаются на `useMeQuery` как на единый источник.
3. **Защита от гонки состояний:** Если бы данные писались в кэш из двух мест (`onSuccess` мутации И `useMeQuery`), при параллельных запросах или обновлении профиля возникает риск рассинхрона — какая версия в кэше актуальна. Один источник записи устраняет эту проблему полностью.
4. **Простота инвалидации после изменения данных:** Обновление профиля или смена role в БД подхватывается через `invalidateQueries` без необходимости вручную прокидывать свежие данные из каждого места, которое теоретически могло бы их вернуть.

**Trade-off (Компромиссы):**
* Один лишний HTTP round-trip на каждый `login`/`register` (~20–100ms в типичных условиях).
* Бэкенд дважды выполняет сборку `UserResource` для одного логического события — не создаёт доп. нагрузки на БД (модель `User` уже в памяти из сессии), только на сериализацию.

**Когда пересматривать (Триггер для рефакторинга):**
При росте нагрузки, где экономия одного round-trip на login/register становится измеримо значимой (например, высокочастотные повторные авторизации в тестах/интеграциях), можно перейти на `queryClient.setQueryData()` прямо из тела ответа `login`/`register`, оставив `useMeQuery` как fallback для случаев без свежего login-события. На текущем масштабе проекта такая оптимизация преждевременна.

### AUTH-13: Signed URL подписывает registration token, не user_id

**Status:** Accepted (supersedes AUTH-1)

**Выбрали:** `URL::temporarySignedRoute` продолжает использоваться как механизм подписи (без изменений в самом Laravel-примитиве), но подписывается **`registration token`**, а не `user_id` — потому что на момент отправки verification-письма `User` в MySQL ещё не существует (см. AUTH-15). `registration token` — идентификатор временной записи `registration:{token}` в Redis. `trustProxies` сужен с `at: '*'` до `env('TRUSTED_PROXIES', '127.0.0.1')` — более безопасный дефолт, не доверяющий всем прокси подряд.

**Почему (Архитектурные преимущества):**

- Все преимущества v1 (просто, нативно, безопаснее OTP, корректная работа за прокси) сохраняются без изменений.
- **Разделение ответственности:** Signed URL отвечает за подлинность и срок действия ссылки, а Redis — за временное хранение pending registration до подтверждения email.
- После успешной верификации registration удаляется из Redis, а `User` создаётся в MySQL уже с подтверждённым email — в одной DB-транзакции.

**Trade-off (Компромиссы):**

- В письме отправляется полный URL с подписью (`?signature=...`) — тот же риск, что и в v1.
- **Новое по сравнению с v1:** Pending registration является stateful-состоянием в Redis, поэтому Redis становится частью критического пути регистрации (детали — AUTH-15).

**Смягчение рисков (Mitigation):** Без изменений от v1 — Frontend как прокси, POST-only verification (AUTH-2), очистка URL через `router.replace`.

### AUTH-14: TTL верификационной ссылки и pending registration — единый жизненный цикл, 60 минут

**Status:** Accepted (supersedes AUTH-3)

**Выбрали:** Тот же TTL `60 минут`, но теперь он управляет **двумя** сущностями одновременно: Signed URL (как в v1) И Redis-записью `registration:{token}`.

**Почему (Баланс безопасности, UX и консистентности — обоснование UX/индустриального стандарта из v1 сохраняется):**

- **Единый жизненный цикл:** Signed URL и Redis-запись `registration:{token}` живут одинаковое время. После истечения TTL ссылка становится недействительной, а pending registration автоматически удаляется из Redis.
- **Отсутствие cleanup-задач:** Неверифицированные регистрации не попадают в MySQL, поэтому для их удаления не требуется отдельный Cron или scheduled command — прямое улучшение по сравнению с v1, где идемпотентность (`409`) была единственной защитой, а "мусорные" `User`-записи всё равно оставались в БД навсегда при недоведённой до конца верификации.

**Trade-off (Компромиссы):** Тот же риск "окна атаки" в 60 минут, что и в v1.

**Поведение после истечения TTL:**

- `registration:{token}` больше не существует в Redis.
- Signed URL считается недействительным.
- Создание `User` не выполняется — при v1 к этому моменту `User` уже существовал бы в БД неверифицированным.
- Пользователь должен начать регистрацию заново и получить новую verification link.
- Пока pending registration ещё существует, пользователь может запросить повторную отправку verification email через `resend`.

**Важно:** TTL `60 минут` относится именно к первичной регистрации и её verification flow. Password reset имеет собственный lifecycle и TTL, который не должен автоматически наследоваться из этого AUTH.

**Открытый вопрос (не закрыт на момент записи):** поведение `resend` при повторном запросе — продлевается ли TTL, выдаётся ли новый токен взамен старого или оба остаются валидны до истечения общего окна. Требует явного решения перед реализацией `EmailVerificationController::resend()`.

### AUTH-15: Zero-DB-write pending registration — User создаётся только после verification

**Status:** Accepted (supersedes AUTH-4)

**Выбрали:**
`POST /register` больше не создаёт `User` в MySQL и не диспатчит `event(new Registered($user))` — потому что на этом этапе `$user` физически не существует. Вместо этого данные (`email`, `hashed password`, `first_name`, `last_name`, `phone`) временно хранятся в Redis по ключу `registration:{token}` с TTL (AUTH-14). Для resend используется дополнительный индекс `registration:email:{email}` → `token`. `User` создаётся в MySQL только после успешной проверки Signed URL, в рамках DB-транзакции, сразу с `email_verified_at = now()`.

**Почему (устраняет корневую причину ISSUE-2, а не патчит симптом):**

- v1 полагался на `MustVerifyEmail` + ручной `Registered`-диспатч именно потому, что `User` создавался мгновенно на `/register`. Это и есть источник ISSUE-2: неверифицированная, потенциально чужая запись немедленно резервирует `email` в `UNIQUE`-индексе `users.email`.
- Zero-DB-write устраняет это полностью: пока email не подтверждён, в `users` нет никакой записи, которую нужно было бы резервировать, чистить или анонимизировать.
- Redis TTL (AUTH-14) автоматически удаляет незавершённую регистрацию — cron для очистки `users` не нужен вообще, в отличие от TTL-cleanup варианта, который рассматривался и был отклонён при разборе ISSUE-2.
- Race-condition защита из v1 (`ModelNotFoundException` при преждевременном листенере) снимается сама собой — писать в БД вообще нечего до момента verification.

**Контракт verification:**

- Signed URL (AUTH-13) содержит `registration token`, а не `user_id`.
- Backend проверяет подпись и наличие `registration:{token}` в Redis.
- В рамках DB transaction создаётся `User` с `email_verified_at = now()`.
- После успешного commit pending registration удаляется из Redis.
- Пользователю создаётся сессия только после успешной verification.

**Trade-off (Компромиссы):**

- Отказ от стандартного Laravel registration flow (`Registered` → `SendEmailVerificationNotification`) в пользу собственного pending-registration flow — `MustVerifyEmail` больше не является механизмом первичной регистрации.
- **Redis становится обязательной зависимостью для регистрации** — что в v1 было лишь опциональным ускорением (сессии), теперь это critical path. Недоступность Redis блокирует создание новых аккаунтов целиком.
- Pending registration содержит hashed password в Redis (не plaintext, но всё же чувствительные данные вне MySQL).

**Граница ответственности:** Без изменений от v1 — `AuthService` → register/login/logout; email verification → отдельный `EmailVerificationController` (AUTH-6); pending registration → Redis; user creation → verification flow.

**Открытый вопрос (не закрыт на момент записи):** поведение при коллизии двух одновременных регистраций на один email до истечения TTL первой попытки — вторая попытка должна получать `422` (email "занят" первой pending-регистрацией) или перезаписывать `registration:email:{email}` (тем самым отбирая слот)? Оба варианта валидны, поведение не зафиксировано.

### AUTH-16: Последовательная отправка verification и welcome email

**Status:** Accepted (supersedes AUTH-7)

**Выбрали:** На этапе регистрации отправляется только `VerifyEmailNotification`. `WelcomeNotification` отправляется только после успешного подтверждения email и создания `User`.

**Почему (снимает оба trade-off'а v1, а не просто UX-предпочтение):**

- v1 держал одновременную отправку как единственный вариант в момент записи, с явным триггером на пересмотр: "переход на sequential flow, если верификация будет строго после `User`". AUTH-15 делает этот триггер неизбежным — раз `User` физически не существует до verification, `WelcomeNotification` **не может** быть отправлено раньше, чем в v1 боялись "склеивания писем" — сама архитектура закрывает проблему, а не только формулировка темы письма.
- Не отправляются Welcome-письма для незавершённых, abandoned registrations — раньше это было UX-пожеланием (v1 mitigation), теперь это гарантия архитектуры (нет `User` → нечему слать Welcome).
- Уменьшается лишний SMTP-трафик на потенциально фейковые адреса — прямое улучшение над риском "нагрузка на репутацию SMTP-домена" из v1 trade-off.

**Новый flow:**

```text
POST /register
    ↓
Redis pending registration
    ↓
VerifyEmailNotification
    ↓
пользователь открывает ссылку
    ↓
POST /verify
    ↓
создание User + email_verified_at
    ↓
WelcomeNotification
    ↓
создание session
```

**Trade-off (Компромиссы):**

- Welcome-письмо приходит позже, чем в v1 (было мгновенно, стало — после клика по ссылке).
- Если пользователь никогда не подтвердит email, Welcome-письмо вообще не будет отправлено — ожидаемое поведение, не баг.
- Требуется отдельный вызов `WelcomeNotification` внутри verification-flow (не через `Registered`-событие, которое здесь не используется — см. AUTH-15).

**Граница ответственности:** `VerifyEmailNotification` → отправляется после создания pending registration. `WelcomeNotification` → отправляется только после успешного создания verified `User`.

**Когда пересматривать:** Без изменений от v1 — CRM integration, бонусы, marketing automation могут потребовать выноса в отдельный application service/event-driven flow.

### AUTH-17: Гранулярное применение middleware 'verified' + guest-first browsing

**Status:** Accepted (supersedes AUTH-8)

**Почему решение пересмотрено:**

- **ISSUE-2 (`issues-list.md`):** Создание `User` до подтверждения email (v1) позволяло любому человеку зарегистрироваться на `someone-else@gmail.com` без доступа к этому ящику. Уникальный индекс `users.email` фактически резервировал чужой адрес до удаления записи.
- **Проблема TTL-cleanup:** Рассматривался вариант удаления неверифицированных аккаунтов через Cron — отклонён, т.к. лишь ограничивал время блокировки, оставляя временные регистрации в `users` и требуя отдельной cleanup-инфраструктуры.
- **Account Restoration:** Такой подход пересекался бы с логикой soft-delete и будущего восстановления аккаунтов через `withTrashed()` (ISSUE-1).

**Выбрали:**

1. **Guest-first browsing:** Каталог доступен без аккаунта. Wishlist хранится на клиенте (`localStorage`) и не требует backend identity — переносится в аккаунт отдельной задачей при регистрации/логине.
2. **Zero-DB-write pending registration** — механизм полностью описан в AUTH-15.
3. **Signed URL на registration token** — механизм полностью описан в AUTH-13.
4. **Session only after verification:** До подтверждения email пользователь не имеет ни `User`, ни сессии. После `POST /register` отображается только сообщение о необходимости проверить почту.

**Обновлённый контракт доступа к API-маршрутам** (заменяет таблицу из AUTH-8 v1 целиком — изменилась не только колонка `verified`, но и семантика доступа guest/account):

| Группа маршрутов | Эндпоинты | Кто может | `auth:sanctum` | `verified` | Обоснование |
|---|---|---|---:|---:|---|
| **Public Catalog** | `GET /products`, `/categories` | Guest + Account | — | — | Доступно всем, включая SEO-роботов. |
| **Wishlist (guest)** | `localStorage` | Guest | — | — | Не требует личности пользователя; перенос в аккаунт — отдельная задача. |
| **Registration & Verify** | `/register`, `/verify`, `/resend` | Guest → Account | ❌ | ❌ | Работают с Redis pending registration, а не с `users`. |
| **Login** | `/login` | Account | ❌ | ❌ | Требует существующего, то есть уже верифицированного, `User`. |
| **Session & Profile** | `GET /me`, `POST /logout`, `/profile/edit` | Account | ✅ | ❌* | Неверифицированного `User` в MySQL больше не существует; сессия выдаётся только после verification. |
| **Cart Operations** | `GET/POST /cart` | Account | ✅ | ❌* | Доступно только существующим пользователям, которые уже прошли verification. |
| **Checkout & Financials** | `POST /checkout`, `/orders`, `/payments` | Account | ✅ | ✅ | **Критическая зона.** Проведение транзакций разрешено только верифицированным пользователям. |

\* `verified` фактически избыточен для `/me`, `/logout`, `/profile` и `/cart`, поскольку по архитектуре любой существующий `User` уже имеет подтверждённый email. Middleware может оставаться как defense-in-depth, но не является механизмом первичной защиты.

**Ключевое отличие от v1:** в v1 "Cart Operations" была отдельным пунктом "не требует verified" именно потому, что было чего требовать — гостю разрешалось наполнять корзину без аккаунта вообще (не указано явно в таблице v1, но подразумевалось soft onboarding'ом). В v2 корзина требует `auth:sanctum` — гостевые действия (wishlist, browsing) полностью вынесены на клиент, что делает "мусорные записи в БД от неверифицированных пользователей" (trade-off v1) неприменимыми: мусора создавать некому, пока `User` не существует.

**Trade-off (Компромиссы):**

- **Resend verification:** Больше нельзя опираться на `user_id`, поэтому требуется дополнительный Redis-индекс `registration:email:{email}`.
- **Повторный клик:** После успешной verification `registration:{token}` удаляется. Поэтому повторный клик не может вернуть прежний `409 email_already_verified` (как было в v1 через идемпотентность `markEmailAsVerified()`). Требуется отдельная обработка — короткоживущий `verified:{token}` marker или `410 Gone`. **Не закрыто на момент записи.**
- **Redis dependency:** См. AUTH-15.
- **User Enumeration:** Риск из AUTH-11 сохраняется в суженном виде — см. примечание там.

**Связь с ISSUE-1 (Account Restoration):** Soft-delete и `withTrashed()` применяются только к уже существующим, верифицированным пользователям. Pending registration в Redis не является аккаунтом и не участвует в логике восстановления.

**Открытые вопросы, не закрытые на момент записи (см. `issues-list.md`):**

- Коллизия двух одновременных регистраций на один email (дублируется из AUTH-15).
- Rate limiting конкретно на `/resend` отдельно от `/register` (AUTH-11 покрывает только `/register`).
- Anonymization vs generated column для `email_active` при будущем soft-delete verified-пользователей (ISSUE-1) — направление намечено (generated column, не anonymization, из-за конфликта с `withTrashed()`), формальный AUTH ещё не написан.

### AUTH-18: Session state через `/me` — обновлённый контракт после zero-DB-write

**Status:** Accepted (supersedes AUTH-12)

**Контекст:**
В v1 `/register` возвращал `UserResource` (тот же, что и `/me`), но фронтенд его игнорировал ради единого источника правды. После перехода на zero-DB-write (AUTH-15) это стало не просто архитектурным предпочтением, а необходимостью: `/register` **физически не может** вернуть `UserResource`, потому что `User` на этом этапе не существует — он создаётся только после verification.

**Выбрали:**
`GET /api/v1/auth/me` остаётся единственным источником истины для текущего authenticated user — сама позиция unchanged от v1, но её обоснование расширяется.

- `sessionApi.login()` не использует `UserResource` из response body (как и в v1).
- `sessionApi.register()` **не ожидает** `UserResource` вообще — не "игнорирует" (как в v1), а типизирован под ответ вида `{ message: string }` ("проверьте почту").
- После успешного login frontend обновляет состояние через `useMeQuery` (как в v1).
- После успешной email verification frontend также обновляет состояние через `useMeQuery` — новый кейс, которого не было в v1 (verification раньше не создавала сессию впервые, а лишь помечала существующего `User`).
- При первоначальной загрузке приложения frontend всегда проверяет `/me` (как в v1).

**Почему (аргументы 1–4 из v1 остаются в силе без изменений — устойчивость к повторным визитам, консистентность между вкладками, защита от гонки состояний, простота инвалидации):**

5. **Новое — совместимость с zero-DB-write регистрацией:** После `/register` пользователь ещё не authenticated в принципе (не просто "мы не используем токен из ответа", а "сессии физически нет"), поэтому frontend не пытается получить `/me` как часть самой регистрации, а показывает pending-state ("проверьте почту"). После verification session создаётся backend впервые, после чего `/me` становится источником актуального `UserResource`.

**Frontend flow (обновлён под AUTH-15/17):**

```text
Initial app load
      ↓
GET /me
      ↓
401 → Guest
200 → Authenticated User


POST /login
      ↓
Sanctum session
      ↓
invalidate/refetch /me
      ↓
Authenticated User


POST /register
      ↓
Redis pending registration
      ↓
Guest + "Check your email"


POST /verify
      ↓
User created + Sanctum session
      ↓
invalidate/refetch /me
      ↓
Authenticated User
```

**Trade-off (Компромиссы):**

- Дополнительный `GET /me` после login и **теперь также** после verification (в v1 такого кейса не было — trade-off вырос на одну точку).
- `/register` больше не возвращает `UserResource` вообще (в v1 — возвращал, но игнорировался). Frontend должен обрабатывать registration как отдельный `pending verification` state — новое требование по сравнению с v1, где после `/register` фронт сразу мог считать пользователя authenticated (просто перепроверял через `/me`).

**Граница ответственности:** Без изменений от v1 — Auth mutations выполняют действие; `/me` сообщает текущее состояние; TanStack Query хранит server state; Zustand не используется как источник истины для `User`.

**Когда пересматривать:** Без изменений от v1.

## Known / Accepted Risks (Принятые риски)

> Таблица отражает текущую (v2, zero-DB-write) архитектуру.

| Риск | Уровень | Смягчение | Статус |
| ----------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| Signed params в query string фронта | Medium | `router.replace` после verification + `Referrer-Policy` на фронте | Accepted |
| Автоверификация роботами (Safe Links) | Medium | Next.js перехватывает входящий `GET` и отправляет явный `POST` запрос на backend | Accepted |
| Replay атака на verification URL | Low | После успешной verification `registration:{token}` удаляется из Redis, поэтому повторное использование того же token не может повторно создать аккаунт | Accepted |
| Race condition при verification | Low | Создание `User` выполняется внутри DB transaction с уникальным `email`; pending registration удаляется из Redis только после успешного commit | Accepted |
| Синхронный SMTP блокирует HTTP-поток | Low | Осознанный компромисс ради простоты отладки на этапе разработки и MVP (см. AUTH-5) | Accepted |
| Redis недоступен во время регистрации | Medium | Redis является частью critical path; registration не создаётся в MySQL без успешного сохранения pending registration | Accepted |
| Pending registration содержит hashed password в Redis | Medium | Password хранится только в hashed form, registration имеет короткий TTL, Redis не должен логировать содержимое ключей | Accepted |
